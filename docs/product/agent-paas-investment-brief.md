# Agent Hosting / Agent PaaS 立项论证草案

> 状态：业务讨论稿
>
> 日期：2026-07-29
>
> 受众：产品经理、BA、AI 应用负责人、平台工程负责人、SRE、基础设施负责人

## 1. 一句话立项主张

建设企业统一的 Agent 生产运行与治理底座，让开发团队把已经构建好的 OCI Agent 镜像，通过一次标准化发布，变成具备稳定访问地址、会话亲和、版本管理、实例运维、流量约束和全链路审计能力的生产服务，而不需要每个团队分别申请并拼装 Kubernetes、负载均衡、域名证书、网络策略、日志监控和发布脚本。

对管理者而言，这不是再造一个 Kubernetes 控制台，而是补齐“Agent 原型完成”到“Agent 生产可用且受控”之间缺失的统一基础设施层。Hosting 是第一块可交付能力，长期目标是让企业内每个 Agent 都可发现、可约束、可追踪、可审计。

## 2. 为什么值得现在投资

### 2.1 市场已验证“Agent 专用托管层”正在成为独立产品

- 阿里云 AgentRun 将 AgentRuntime、会话亲和、Serverless 弹性、版本、Endpoint、灰度和可观测组合成完整的生产旅程。[阿里云 AgentRun](https://help.aliyun.com/zh/functioncompute/what-is-agentrun)
- 腾讯云把“Agent 应用托管”与“Agent 沙箱执行”拆成两类产品；云函数 Agent 执行引擎专门处理镜像部署、访问地址、会话亲和、弹性和日志。[腾讯云 Agent 执行引擎](https://cloud.tencent.com/document/product/583/123905)
- 火山引擎 AgentKit 把“智能体运行时”列为与工具沙箱、记忆、知识、网关和观测并列的基础能力，并提供运行时版本、发布记录和实例查询。[火山引擎 AgentKit](https://www.volcengine.com/docs/86681?lang=zh)
- AWS AgentCore Runtime 和 Microsoft Foundry Hosted Agents 也都把容器化 Agent 的运行、会话、身份、弹性和观测作为托管基础设施能力。[AWS AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html)、[Microsoft Foundry Hosted Agents](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents)
- AWS、腾讯和火山还把 Runtime 与 Gateway、Policy、Guardrail 分层：运行时负责托管，网关负责受控流量，策略与安全围栏负责语义风险和工具动作。这说明企业 Agent 基础设施的最终形态不只是“跑起来”，还要形成不可绕过的治理链路。[AWS AgentCore Policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html)、[腾讯云 AI Agent 安全网关](https://cloud.tencent.com/document/product/1627/78608)、[火山 AgentKit 安全围栏](https://www.volcengine.com/docs/86681/2178840)

这说明行业已经从“提供模型 API”进入“提供 Agent 生产运行底座”的阶段。

### 2.2 企业内部的实际缺口

以下内容目前属于待访谈验证的业务假设：

- Agent 团队能快速完成 Demo，但生产上线仍要跨多个平台和团队申请资源。
- 不同 Agent 项目各自维护 Deployment、Service、Ingress、HPA、证书、日志和发布脚本。
- 已有安全沙箱、模型网关和网络平台等企业能力没有被串成 Agent 上线时自动生效的治理路径。
- 会话亲和、SSE 长连接、优雅摘流等 Agent 特有要求没有形成统一标准。
- 平台团队难以回答“有哪些 Agent 正在运行、属于谁、使用了多少资源、是否健康、运行哪个版本”。
- 安全团队难以回答“谁调用了 Agent、Agent 又访问了哪些模型/工具/数据、哪项策略允许了这次动作、能否还原完整证据链”。
- 业务团队通常只能看到 Pod 或基础设施错误，无法获得以 Agent 环境和发布版本为中心的运维视图。
- 集群容量、套餐、配额与 Agent 实际部署之间缺少统一资源账本。

若这些假设在内部访谈中成立，就存在明确的平台化投资空间。

## 3. 目标用户与购买者

| 角色 | 当前任务 | 主要痛点 | 平台提供的价值 |
|---|---|---|---|
| Agent 开发工程师 | 将 Agent 代码交付生产 | 需要理解并操作大量基础设施；环境不一致；排障链路长 | 提交镜像和少量运行参数即可获得可调用 Endpoint |
| Agent 应用负责人 | 对可用性、发布和业务接入负责 | 不知道实际运行版本、容量和风险；上线依赖多人协作 | 统一查看状态、版本、实例、入口、告警和操作记录 |
| 平台工程 / SRE | 承担集群、发布和故障处理 | 每个团队做法不同；重复脚本多；缺少统一对账和审计 | 标准套餐、自动收敛、实例自愈、统一运维入口 |
| 资源池管理员 | 管理租户专属集群与容量 | 资源分散，缺少面向 Agent 的容量视图和放置策略 | 注册集群、采集容量、维护租户归属并输出放置决策 |
| 安全、网络与 IAM 管理员 | 管理凭证、域名、网络和权限 | 明文密钥、手工证书、临时网络规则难治理 | 只允许引用受管 Secret、证书、网络和身份 Profile |
| PM / BA / 管理者 | 决定是否投资共享平台 | 很难量化重复建设和交付摩擦 | 用交付周期、失败率、工单量、资源利用率衡量收益 |

主要日常用户是 Agent 开发者和应用负责人；真正的项目出资人通常是 AI 平台负责人、研发效能负责人或基础设施负责人。

## 4. 要解决的核心业务问题

### 问题一：从镜像到生产服务的路径不标准

同一份 Agent 镜像在不同团队手中可能使用不同的部署模板、健康检查、超时、日志和域名策略。平台需要提供一条“黄金路径”，让常规 Agent 不再重新设计基础设施。

### 问题二：Agent 有不同于普通 Web 服务的运行特征

- 多轮调用希望保持实例亲和；
- 响应常使用 SSE，处理时间可能较长；
- 模型、工具和数据库调用造成延迟与并发波动；
- 发布或缩容时需要先摘流，再等待存量请求结束；
- 实例变化后会话可能重新映射，因此权威状态必须外置。

如果继续完全使用通用应用平台，以上约束会被分散到每个业务项目中。

### 问题三：基础设施对象不能直接表达业务状态

Pod 是运行实例，但“Pod Running”不等于“Agent 环境已经可访问”。生产可用还取决于：

- 期望版本是否部署完成；
- 就绪实例是否达到目标数量；
- LB 后端是否同步；
- 域名和证书是否正常；
- 健康检查是否通过；
- Endpoint 是否指向正确 Revision。

平台需要提供一个面向 Agent 环境的综合状态，而不是让用户自行拼接多个系统的状态。

### 问题四：规模增长后缺少统一治理

目标规模为数千个运行环境、数万个实例和几十个租户专属集群。依靠人工脚本和逐集群操作会迅速遇到一致性、权限、审计、容量和故障恢复问题。

### 问题五：Agent 不只是被调用的服务，也是会主动行动的主体

普通 Web 服务的主要风险通常集中在入口访问，而 Agent 会代表用户或系统主动调用模型、MCP、工具、数据库和外部 API。只给 Agent 一个可访问域名并不足以投入生产，还需要回答：

- 哪个用户或系统触发了本次执行；
- Agent 可以访问哪些目标，是否能直接绕过企业模型或工具网关；
- 高危操作是否被拒绝或要求二次确认；
- 提示词攻击、敏感信息和异常调用是否被识别；
- 控制面变更、流量路径、策略决策和最终动作能否关联还原。

这使统一审计、入站/出站控制和安全护栏成为长期平台价值，而不是单个 Agent 团队各自实现的附属代码。

## 5. 产品承诺

平台对业务用户提供七项明确承诺：

1. **可部署**：有效的 OCI 镜像和最小配置可以形成可运行的 Agent 环境。
2. **可访问**：部署成功后自动获得平台 HTTPS Endpoint，可选绑定企业域名。
3. **可发布**：每次部署配置形成不可变 Revision，可以观察发布过程并回滚。
4. **可运维**：能够查看实例、健康、日志、指标、失败原因和操作记录。
5. **可治理**：资源只能进入租户专属集群，并遵循平台套餐、配额、网络、身份和证书策略。
6. **可约束**：每个生产环境都有明确的入站、出站和工作负载安全策略，实际生效状态可见。
7. **可审计**：所有外部可观察、会产生业务或安全影响的操作都有身份、上下文、策略决策、结果和关联 ID；不以采集模型思维链为目标。

## 6. MVP 范围

### 范围内

- 租户和项目上下文接入现有 IAM。
- OCI 镜像部署，发布时固化镜像 Digest。
- Agent 运行环境及不可变 Revision。
- RuntimePlan 套餐选择。
- 手工副本数和启动、停止、更新、回滚、删除。
- HTTP/HTTPS 与 SSE。
- 平台默认 HTTPS Endpoint。
- Header 会话亲和；同一实例可承载多个会话。
- Agent 实例列表、状态和基础运维操作。
- HTTP 健康检查。
- 普通环境变量与 Secret 引用。
- 日志、基础指标、控制面操作审计和平台自动执行审计。
- Request ID、Operation ID 和 Trace ID 贯穿入口、Revision、实例和平台执行链路。
- 复用既有 LB 的 Ingress Profile，统一表达可见性、认证、TLS、限流、超时和来源约束。
- 复用既有网络能力的 Egress Profile，至少区分隔离、受限内网、批准的模型/工具和审核公网访问。
- 强制工作负载安全基线：固定镜像 Digest、非特权运行、受管 Secret、工作负载身份和资源限制。
- `SecureTaskProfile`：Agent 部署可绑定现有的短期安全沙箱，高风险 Shell、浏览器、代码和文件任务不得回退到主容器执行。
- 每环境独立模型身份，禁止共享长期模型 API Key；优先通过企业模型网关代持供应商凭证。
- 安全隔离操作：LB 摘流、阻断出站、吊销身份和不可变实例替换。
- 已有租户专属 Kubernetes 集群的注册、健康和简单放置。
- 既有 LB 的域名、后端和健康检查集成。
- CRUD 权威状态、事务 Outbox、MQ 快速唤醒、周期对账兜底。

### 明确不在 MVP

- Agent 无代码/低代码编排。
- Prompt、模型、工具、Memory、Knowledge 和评测平台。
- 自建代码或浏览器安全沙箱；MVP 只集成企业已有短期任务服务。
- 源码构建和 CI/CD。
- 显式 Session 资源、Session CRUD、会话历史存储。
- 一会话一实例和会话级存储挂载。
- WebSocket、gRPC、A2A、MCP 协议托管。
- 缩容到零、毫秒冷启动和预测伸缩。
- 多版本流量灰度和完整流量治理。
- 自研提示词攻击、内容安全和敏感数据检测引擎。
- 通用 MCP / Tool Gateway、高危业务动作策略引擎和人工审批中心。
- Kubernetes 集群创建、节点池扩容和升级。
- 商业计量计费。

## 7. 可量化业务收益

不要在立项会上承诺未经基线验证的百分比。建议先收集现状，再以试点设目标。

| 价值维度 | 建议基线 | MVP 验证指标 |
|---|---|---|
| 交付效率 | 镜像完成到获得生产入口的端到端耗时 | 平台自助发布耗时；人工等待时间；涉及团队数 |
| 变更可靠性 | Agent 发布失败或回滚次数 | 发布成功率；回滚耗时；失败定位耗时 |
| 运维效率 | 与 Agent 部署、扩容、域名、日志相关的工单量 | 单 Agent 月均工单数；人工操作步骤数 |
| 故障恢复 | 发现和恢复实例、路由异常的时间 | MTTD、MTTR；自动恢复比例 |
| 标准化 | 使用自定义脚本和模板的 Agent 数量 | 接入平台的 Agent 占比；标准套餐覆盖率 |
| 资源治理 | 各集群可用容量和实例资源使用情况 | 容量可见率；放置失败率；闲置资源比例 |
| 安全治理 | 明文密钥、手工证书、无限制公网出站和不可追责操作数量 | Secret 引用覆盖率；操作审计覆盖率；Ingress/Egress Profile 生效率 |

## 8. 建议的投资闸门

### Gate 1：问题验证

- 访谈至少三类角色：Agent 开发团队、平台/SRE、资源或网络管理员。
- 选取若干已经上线或准备上线的 Agent，复盘实际交付步骤和时间。
- 确认至少两个团队存在重复问题，而不是单个项目的特殊需求。

### Gate 2：MVP 价值验证

- 选择少量、不同框架但都已容器化的 Agent 作为试点。
- 验证从镜像到 Endpoint、发布更新、故障自愈和会话亲和完整闭环。
- 验证生产环境的入站/出站策略生效，且从用户操作到平台执行能够形成关联审计。
- 对比平台前后的交付耗时、人工步骤和排障时间。

### Gate 3：平台化扩展

- 在试点成功后再投资自动伸缩、多版本灰度、更多协议和高级资源池调度。
- 第二阶段可集成企业模型/AI 安全网关，增加 Prompt 与敏感数据护栏、MCP / Tool 级策略和高危操作审批；不把检测引擎塞进 Hosting 核心。
- 只有出现真实需求时，才考虑自建模型、工具、记忆或新的安全沙箱产品；现有短期沙箱继续作为受管外部能力集成。

## 9. 面向 PM / BA 的三十秒表述

> 现在各 Agent 团队可以很快做出 Demo，但生产上线仍要分别处理容器、集群、负载均衡、域名证书、网络权限、审计和发布。更关键的是，企业很难统一回答每个 Agent 由谁发布、谁在调用、可以访问什么、执行了什么以及为何被允许。我们要建设的不是另一个 Agent 编排器，也不是 Kubernetes 控制台，而是企业统一的 Agent 生产运行与治理底座：第一阶段把镜像安全、稳定地变成可访问、可运维、可审计的服务，随后把模型、工具和数据访问纳入统一策略，最终让 Agent 规模化上线而不失控。

## 10. 当前需要通过业务访谈确认的问题

1. 公司目前最痛的是交付速度、生产稳定性、安全治理，还是集群资源利用率？
2. 已有多少 Agent 项目，未来十二个月的接入规模和上线节奏是什么？
3. 当前一次 Agent 上线实际涉及哪些团队、系统和审批？
4. 哪些现有平台能力可以直接复用：IAM、Secret、证书、域名、LB、日志、监控、镜像仓库？
5. 试点团队愿意提供哪些真实镜像和业务流量用于验收？
